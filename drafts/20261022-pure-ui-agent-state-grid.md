## 한줄 요약
에이전트가 UI 코드를 쓰는 비중이 커질수록 질문이 바뀐다. “잘 만들었나?”가 아니라 **“어떤 상태의 화면을 확인했나?”** 다. 디자이너·개발자 Matt Rothenberg의 글이 이걸 아주 시각적으로 보여 준다([원문](https://mattrothenberg.com/notes/pure-ui-agentic-era/)).

## 사례: 초록불 4개, 그런데 버그
요청은 단순했다. “함수 목록 표 각 행에 삭제(Delete) 버튼을 붙여 줘.” 에이전트는 파일 두 개를 고치고, 타입체크 **통과**, 로컬 브라우저 **확인**, 스크린샷까지 붙여 “완료”라고 보고했다.
문제는 개발 서버가 **소유자(Owner) 계정**으로 로그인돼 있었다는 것. 같은 페이지를 **뷰어(Viewer)** 로 열면 머리말엔 “View only(보기 전용)”라고 써 있는데, 표엔 삭제 버튼이 그대로 있었다. 머리말 컴포넌트는 역할을 알았고, 표는 몰랐다.

## 처방: 상태를 ‘펼쳐서’ 본다
- **원칙**: 화면은 상태의 함수다(`ui = fn(state)`) — Vercel의 Guillermo Rauch가 제안한 ‘Pure UI’.
- 예시 대시보드는 입력이 4개다: **역할(소유자/뷰어) · 요금제(Pro/Free) · 결제 상태(정상/연체) · 베타 기능(켬/끔)**. 2×2×2×2 = **16개 화면**.
- 16개를 **격자로 한 판에** 그리자, 에이전트가 본 건 1개였고 뷰어 화면 **8개 모두**에 삭제 버튼이 보였다. 계정 16개를 만드는 것보다 화면 16개를 그리는 게 싸고, 코드 차이(diff)보다 그림 격자가 훑어보기 빠르다.

## 실무로 옮기면
1. 역할·요금제·플래그처럼 **화면을 바꾸는 상태**를 여기저기 숨은 훅·컨텍스트에서 꺼내, 페이지 경계의 **명시적 입력**으로 모은다.
2. **Storybook**으로 중요한 조합을 렌더하고, **Playwright**로 그 상태가 실제 앱에서 도달 가능한지 확인한다.
3. 머지 전 에이전트에게 묻는다: **“어떤 계정·상태로 확인했나?”** 사람도 같은 실수를 하지만, 에이전트는 1개를 보든 16개를 보든 **똑같이 자신 있게** “완료”라고 말한다.

## 왜 중요한가
디자이너가 예전부터 하던 말 — “행복한 화면 하나만 그리지 말라(빈 상태·오류·권한별 화면도 그려라)” — 이 에이전트 시대의 **품질 보증 방법**으로 돌아왔다. 10/20에 소개한 ‘돌아가는 화면으로 검수’(App Canvas·Naksha) 흐름과도 이어진다. 디자인 산출물에 **상태 매트릭스**를 포함하는 습관이 사람과 에이전트 모두의 실수를 줄인다.
