## 한줄 요약
‘컴퓨터 사용’ 에이전트 대부분은 화면을 찍어 보고 좌표를 누른다. Vercel Labs의 **agent-desktop**은 다르다. 운영체제가 장애인 보조 기술용으로 제공하는 **접근성 트리**를 읽어 “이 버튼, 이 입력칸”을 구조로 넘긴다. 11/9 GitStock 주간 트렌딩 2위로, 총 약 2만 별 중 **한 주에 약 1.37만**이 붙었다([GitStock 주간 스냅샷](https://gitstock.org/trending/weekly/2026-11-09), [공식 문서](https://agent-browser.dev/desktop)).

## 어떻게 쓰나 (개념만)
1. **지도 그리기**: 앱의 얕은 골격 스냅샷을 JSON으로.
2. **파고들기**: 필요한 영역만 펼친다.
3. **행동**: 요소의 ref로 클릭·입력. ref에는 그 스냅샷의 ID가 붙어 있어, 화면이 바뀌면 다시 스냅샷을 떠야 한다.
4. **확인**: “성공 응답 ≠ 화면이 바뀜”이므로 마지막에 다시 읽어서 값이 맞는지 본다(계산기 예시: 7 버튼을 누르고 표시창이 7인지 대기·확인).

## 무엇이 아닌가 (문서가 직접 선을 긋는다)
- **에이전트가 아니다**. 관찰→행동→검증 루프는 호출하는 쪽(내 에이전트·스크립트)에 있다. 모델·GUI·대화형 프롬프트가 없고, 명령마다 JSON 하나를 출력하고 끝난다.
- **데스크톱 앱 전용**. 웹 페이지는 자매 도구 agent-browser 몫. Chromium·Electron 앱이면 DevTools 포트를 열어 agent-browser가 붙게 한다.
- **앱이 접근성 정보를 안 내보내면 못 본다**. 픽셀을 보지 않기 때문이다.

## 지원 환경
macOS 13+(AX API, 접근성 권한 필요), Windows 10 1809+(UI Automation), Ubuntu 24.04+(AT-SPI). 세 OS 모두 같은 60개 명령 이름. CLI 외에 C 라이브러리로도 쓴다.

## 왜 중요한가
스크린샷 방식보다 **토큰이 적고, 결과가 결정적이며, 검증이 쉽다**. 대신 접근성 지원이 엉성한 앱에서는 무력하다. 역설적으로, 접근성을 잘 만든 앱이 ‘에이전트 친화적인 앱’이 된다. 같은 주 트렌딩에는 형제 프로젝트 agent-browser(7위권, 약 4.8만 별)도 함께 올랐다.
