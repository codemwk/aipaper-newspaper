## 한줄 요약
TLDR Design(10/19)이 소개한 에세이 한 편의 주장은 이렇다: 디자이너는 건축가가 돌과 철을 이해하듯 **코드를 ‘재료’로** 이해해야 한다. AI가 구현을 맡을수록, 반응형 동작·실제 데이터·로딩·접근성·**실패 상황**을 그림이 아니라 **돌아가는 화면에서** 검수할 수 있기 때문이다. 같은 주말(10/18) 나온 두 오픈소스가 그 방향을 구체적인 도구로 보여 준다.

## ① App Canvas — 내 앱 전체를 ‘디자이너의 캔버스’처럼
개발자 Tom Tang이 공개한 **App Canvas**는 이미 만든 앱을 **줌 아웃해서 한눈에** 보고, 줌 인해서 **진짜 UI를 눌러 보는** 도구다([소개 글](https://tomtang3.ai/blog/introducing-app-canvas/)).
- **화면 목록을 사람이 만들지 않는다**: 코딩 에이전트(Codex·Claude Code 등)가 앱 소스 전체를 훑어 화면·컴포넌트·상태·이동 경로를 찾고, **가짜(합성) 데이터**와 렌더링 장치를 만든다. 별도 목업을 그리지 않고 **원래 UI 코드**를 그대로 쓴다.
- **상태까지 본다**: 정상 화면뿐 아니라 **빈 화면, 로딩, 오류, 권한 거부, 대화상자, 복구** 상태를 캔버스에 펼친다.
- **흐름을 재생한다**: “저장 실패 → 초안 유지 → 재시도”를 고르고 Demo를 누르면, 하나의 앱 세션에서 실제 버튼을 눌러 가며 결과를 확인한다.
- **‘완료’ 기준이 엄격하다**: 소스에서 찾은 목록과 실제 렌더링된 상태를 대조하는 `--complete` 검사를 통과해야 끝난 것으로 본다. 못 찾은 항목은 ‘미완료’로 남는다.
- 공개 데모: **77개 상태, 44개 흐름, 121개 재생 항목**. 캔버스 자체는 **모델을 호출하지 않는다**(에이전트 비용은 별도). MIT, Node.js 22 이상. 뷰어 메뉴는 현재 번체 중국어.

## ② Naksha Studio v6 — AI 디자인 리뷰를 ‘다른 AI’가 반박
**Naksha**는 Claude Code·Cursor·Gemini CLI 등에 들어가는 ‘가상 디자인팀’ 플러그인(30개 역할, 70개 명령)이다. 10/18 나온 **v6.0.0**은 “믿을 수 있는 리뷰”에 집중했다([릴리스 노트](https://github.com/Adityaraj0421/naksha-studio/releases/tag/v6.0.0), [ByteForward](https://bytefwd.com/naksha-v6-claude-code-design-review-dashboard/)).
- **검증된 리뷰**: 리뷰 에이전트가 근거를 남기면, **원래 추론을 보지 못한 별도 검증자**가 각 지적을 확인·기각·보류한다. 별도 에이전트를 못 쓰면 같은 대화에서 다시 보는 ‘약한 방식’임을 밝혀야 한다.
- **AI 없는 디자인 린트**(`/design-detect`, 22개 규칙): UI를 고칠 때마다 자동 실행. 단 대비 검사는 같은 CSS 블록에 선언된 색만 보므로 실제 렌더링 확인은 브라우저가 필요하다.
- **비용 표시**(`/naksha-stats`): 명령별 토큰과 API 정가 기준 **예상 비용**(청구서가 아님).
- **Naksha Live**: 30개 역할의 활동·지적·비용을 보여 주는 로컬 대시보드(127.0.0.1, 토큰 필요, 기본 꺼짐).
- 같은 날 v5.3.0에서는 서로 확실히 다른 시안 2~5개를 비교하는 `/design-variants`와 **취향 기억**이 들어갔다.

## 왜 중요한가
AI가 화면을 빨리 만들수록 디자이너의 일은 **“무엇이 빠졌나”를 찾는 검수**로 옮겨 간다. 실패·빈 화면·권한 거부 같은 상태는 정적 시안에서 가장 자주 빠지는 부분이다. App Canvas는 그걸 **보이게** 하고, Naksha는 AI 리뷰가 그럴듯한 말만 늘어놓지 않도록 **반박 단계**를 넣었다. 둘 다 초기 단계(Naksha 별 수백 개, App Canvas 공개 직후)이니, 작은 화면 하나로 먼저 시험해 보는 걸 권한다.
