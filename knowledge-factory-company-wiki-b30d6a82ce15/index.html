[11/25] 세컨드 브레인: 회사용 LLM Wiki를 ‘공장’으로 — LangChain ‘지식 공장’ 설계, 그리고 맥락 없는 코딩 에이전트는 사내 부품을 55~59%만 썼다는 보고서

LangChain CEO Harrison Chase가 11/21 ‘지식 공장(knowledge factory)’ 설계를 공개했다. 일하는 에이전트가 빠지거나 틀린 지식을 신고하고, 백그라운드의 ‘큐레이터 에이전트’가 정해진 주기로 원자료와 작업 기록을 보며 지식을 고친다. 지식은 스킬(일하는 법)·도메인 지식(사업이 돌아가는 법)·데이터 접근 안내(최신 정보 찾는 법) 세 가지로 나눈다. 같은 주 DesignVerse 보고서는 맥락 없는 프런티어 코딩 에이전트의 정확도가 55~59%, 정리된 맥락을 준 시스템은 92%였다고 주장했다.

분류: 세컨드 브레인

한줄 요약

개인 세컨드 브레인에서 유행한 LLM Wiki(AI가 노트를 쌓고, 연결하고, 점검하는 위키)가 회사 단위로 커지고 있다. LangChain은 이걸 “지식 공장”이라 부르며, 사람이 손으로 관리하지 말고 관리하는 시스템을 만들라고 말한다(LangChain 블로그).

LangChain ‘지식 공장’의 세 부품

  • ① 에이전트가 빈틈을 신고하는 도구. 일하다가 정보를 못 찾거나 틀린 정보를 발견하면 신고하고, 가능하면 고칠 내용을 제안한다.
  • ② 큐레이터 에이전트. 백그라운드에서 정해진 주기로 돈다. 원자료(Notion, Slack 등), 에이전트 작업 기록(trace), 신고 목록을 보고 지식을 고친다. 일하는 에이전트가 직접 고치게 하면 지식이 엉키고 서로 모순된다는 게 이유다.
  • ③ 저장소. GitHub의 스킬 파일, Notion 문서 하나, LangSmith Context Hub, Neo4j 그래프 등 어디든. Chase는 “사실 가장 덜 중요한 부분”이라며 형식을 미리 정하지 말라고 했다.

지식의 세 종류

  • 스킬 — 일하는 법. 회사 방식대로 일하는 절차·지시·스크립트. 동료끼리 말로만 전하던 것을 글로.
  • 도메인 지식 — 사업이 돌아가는 법. 자주 안 바뀌는 사람·제품·경쟁사·정의(예: ARR 계산법).
  • 데이터 접근 안내 — 최신 정보 찾는 법. 데이터를 복사해 두지 말고 “어디에 있고 어떻게 조회하는지”만 관리.
  • 예시: 매출 보고서 에이전트가 BigQuery 열 이름이 바뀐 걸 발견해 신고하고, 재무 담당자가 새 머리말 양식을 지적한다. 그날 밤 큐레이터가 신고와 대화 기록을 보고 관련 스킬 두 개를 고친다. 다음 보고서부터는 처음부터 맞게 나온다.

숫자로 본 ‘맥락’의 차이 (업체 보고서)

  • DesignVerse의 11/19 AI Coding Drift Report는 15~20년 된 100만 줄 이상 사내 코드베이스 15개(항공·은행·국방 등, Ada·C++·COBOL)에서 시험했다(DesignVerse).
  • 맥락 없는 프런티어 에이전트 2종의 정확도 55~59%, 정리된 사내 맥락을 준 시스템 92%. 같은 질문을 두 번 했을 때 답이 같은 비율은 61~69% 대 97%.
  • 실패 유형 1위권은 사내에 이미 있는 부품을 놔두고 새로 만들거나 공개 라이브러리로 바꾸는 것이었다.
  • 주의: 업체 자체 연구이고, 같은 모델에서 맥락만 바꾼 비교가 아니라 ‘시스템 전체’ 비교다.

왜 중요한가

지난번 저장하신 LLM Wiki·Obsidian 에이전트 메모리 흐름과 이어지는 소식이다. LangChain은 Deep Agents 예제에 실제로 llm-wiki(수집·질문·점검) 예제도 두고 있다. 개인 볼트에 바로 옮길 만한 아이디어는 두 가지다.

  • “쓰는 에이전트”와 “정리하는 에이전트”를 나눈다. 어제 obsidian-wiki의 ‘쓰기 거부권·되돌리기’와 같은 문제의식이다. 매일 쓰는 봇은 신고만, 주 1회 큐레이터가 정리.
  • 데이터는 복사하지 말고 위치를 적는다. 트레이딩 기록·전략 문서처럼 원본이 따로 있는 건, 볼트엔 “어디 있고 어떻게 읽는지”만 남기는 게 덜 낡는다.
