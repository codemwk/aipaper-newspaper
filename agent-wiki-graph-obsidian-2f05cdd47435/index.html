AiPaper 뉴스 · 세컨드 브레인 / PKM · 2026-11-11 07:00 KST

[11/11] 회의 녹음 28개를 옵시디언 위키로: 에이전트 9개가 한 볼트를 같이 쓰는 법 — ‘출처는 불변, 모르면 [UNVERIFIED]’

Mike Moore가 11/9 Claude Code로 한 주치 회의 녹음·데모 저장소·블로그를 옵시디언 LLM 위키에 넣은 실제 과정을 공개했다. 핵심은 루트 스키마 파일의 세 규칙(라우팅 질문, 출처 규칙, 팬아웃 목표)과 병렬 에이전트의 ‘소유권’ 규칙. 1,718페이지·고아 페이지 0개까지 갔다.

분류: 세컨드 브레인 / PKM

무엇인가

Karpathy의 LLM Wiki 아이디어를 실무에 깊게 적용한 사례다. 에이전트는 매 세션 시작 시 일주일치 회의, 만든 데모, 겪었던 함정을 이미 알고 있다. 모델이 기억해서가 아니라, 사람이 옵시디언으로 여는 마크다운 위키를 읽고 쓰기 때문이다. 예제 볼트가 담긴 스타터 킷은 themsquared/agent-wiki-graph(원문).

구조: 두 층

  • 고객(계정)별 볼트: 사람, 단계, 막힌 것, 누가 뭐라고 했는지. _raw/(불변 원본), meetings/, people/, topics/, 자동 재생성되는 status.md.
  • 루트 기술 층: 특정 고객을 넘어 오래 남는 것 — 함정(concepts/), 제품 버전별 동작, 데모 환경. 복리로 쌓이는 건 이쪽이다.
  • 에이전트 기본 메모리는 한 줄 색인만 두고, 각 줄이 위키 페이지를 가리킨다.

에이전트를 움직이는 세 규칙 (루트 CLAUDE.md)

  • 라우팅 질문: “이 사실은 이 고객에 대한 것인가, 제품에 대한 것인가?” 고객 것은 볼트로, 일반화되는 건 concepts/로 보내고 양쪽에서 링크.
  • 출처 규칙: 읽지 않은 사실은 쓰지 않는다. 확인 안 된 주장은 [UNVERIFIED]와 무엇이 확인해 줄지 함께 표시. “X 지원” 대신 “2026-10-14 실제 클러스터에서 재현”, 버전은 항상 고정.
  • 팬아웃 목표: 진짜 소스 하나는 5~15페이지를 건드려야 한다. 한 페이지만 고쳤다면 덜 넣은 것.

병렬 에이전트가 한 볼트를 망치지 않는 법

에이전트 9개(고객별 6 + 데모·블로그·메모리 매핑 3)가 동시에 썼다. 규칙은 소유권: 각 하위 에이전트는 볼트 하나만 쓴다. index.md·log.md·기존 concepts/ 같은 공유 파일은 오케스트레이터만 고치고, 하위 에이전트는 “제안 편집”을 보고서로 돌려준다. 내부 회의 에이전트는 다른 고객 7곳에 대한 사실을 찾았지만 직접 쓰지 않고 넘겼다.

현장에서 배운 함정 (가장 쓸모 있는 부분)

  • 화자 이름표는 생각보다 자주 틀린다. 이름이 붙은 라벨도 추측일 뿐. 본인이 자기 이름을 3인칭으로 부르면 라벨 오류 신호.
  • 녹음기 요약은 전사 오류를 사실로 재진술한다. “Kubernetes 1.33”이 요약에서 “1.3”이 됐다. 사실은 전사본에서만 뽑는다.
  • 통화가 끝난 뒤 계속 녹음된 집안 소리, 개인 통화는 원본 저장 전에 걸러야 한다(_raw/는 불변이라 나중에 못 지운다).
  • 링크 검사기를 돌리니 1,658페이지 중 고아 페이지 108개. 고객별 색인에 전체 경로 링크 지도를 붙여 최종 1,718페이지·14,458링크·고아 0.

왜 중요한가

지난번 저장하신 LLM Wiki·vault-bridge·obsidian-wiki 흐름에서 가장 ‘운영 매뉴얼’에 가까운 글이다. 특히 “위키에서 가장 많이 링크된 페이지는 제품이 아니라 에이전트가 읽는 도구가 거짓말하는 방식(함정 목록)이었다”는 관찰은, 세컨드 브레인을 에이전트용으로 키울 때 무엇부터 적어야 하는지 알려 준다. 저자가 다음에 만들 것은 git 커밋에서 뽑는 주간 변경 페이지 — “지금 무엇이 참인가”뿐 아니라 “지난주 이후 무엇이 바뀌었나”.

주의

저자 말대로 스키마 파일은 보안 장치가 아니라 라우팅 장치다. 협조적인 에이전트를 정리할 뿐, 악의적 입력을 막지 못한다. 업무 위키에는 고객 데이터가 들어가니 저장소 접근 권한을 관리할 것.
